## 速览

- `cache` 以 `cache line` 为基本传输和一致性单位；地址通常拆成 `tag / index / offset`，通过 `set + way` 组织，`tag` 用于查找某个地址**在不在组内**（使用并行比较），`index` 用于**定位组**，相同 `index` 的地址会被映射到同一个组里。
- `MESI` 描述一条 `cache line` 在多核中的一致性状态：`M/E/S/I`。其中 `M/E` 可以本地写，`S` 只能本地读，写之前要先拿独占权限。
- 一致性协议主要解决**同一地址**的问题：同一 `cache line` 的读写必须有一致的可见性；它不自动保证**不同地址**之间的观察顺序。
- `store buffer` 位于执行流水线和 `L1D` 之间：`store` 先进入 `store buffer`，后续同地址 `load` 可以从中转发数据，等拿到写权限后再真正并入 `L1D`。
- `invalidate queue` 位于本地 `coherence controller` 和 `L1 cache` 之间：失效请求可以先入队、后更新本地缓存状态；但后续新访问不能因此公开违反同一地址上的缓存一致性。
- 实际编程里最常见的性能问题是 `cache line bouncing` 和 `false sharing`：多个线程频繁写同一条 `cache line`，即便写的是不同变量，也会引发所有权来回转移。

## 映射方式

### 组相联

地址通常可以拆成三部分：

- `offset`：表示该地址在一个 `cache line` 内的偏移，位数等于 `log2(cache line 大小)`
- `index`：表示该地址映射到哪个 `set`，位数等于 `log2(set 数量)`
- `tag`：表示该地址对应的高位标识，用来在选中的 `set` 中判断具体命中了哪个 `way`

![[组相联映射|800]]

其中：

set 数 = cache 大小 / (way 数 × cache line 大小)

例如，一个 `64KB` 的 cache，采用 `4-way` 组相联，`cache line` 大小为 `64B`，则：

set 数 = 64KB / (4 × 64B) = 256

所以：

- `index` 需要 `log2(256) = 8` 位
- `offset` 需要 `log2(64) = 6` 位
- 剩下的高位就是 `tag`

访问流程可以概括为：

1. 用 `offset` 确定数据在 `cache line` 内的字节位置
2. 用 `index` 定位到对应的 `set`
3. 在这个 `set` 的所有 `way` 中并行比较 `tag`
4. 若某个 `way` 的 `tag` 匹配且该行有效，则命中；否则未命中，需要从下层 cache 或内存中取回整条 `cache line`

### 全相联

整个cache被作为一个组，除了 offset 的所有位都用来作为 tag 使用。
好处是任何地址都可以随便放，坏处是比较器会变得特别复杂，太贵了。

### 直接映射

一路就是一个组，index 的位数由缓存行数量决定（log(缓存行数)），地址中除了 offset 和 index 的剩余位作为 tag 使用。
好处是结构简单，命中判断快，坏处是容易冲突。如果两个内存块被映射到一个组，后面的那个就会把前面那个顶掉。

## 缓存一致性协议

### MESI Protocol

#### 四种状态

- `M` (`Modified`)：该缓存行**只存在于当前 cache 中**，并且已经被修改过，主存中的内容可能还是旧值；**允许本地读和本地写**
- `E` (`Exclusive`)：该缓存行**只存在于当前 cache 中**，但还没有被修改，和主存内容一致；**允许本地读和本地写**，执行本地写后变为 `M`
- `S` (`Shared`)：该缓存行可能同时存在于多个 cache 中，内容和主存一致；**允许本地读，不允许直接本地写**，写之前需要发起 `BusUpgr`，成功后完成写入并变为 `M`
- `I` (`Invalid`)：该缓存行当前无效，不能使用；**不允许本地读，不允许本地写**。读之前需要发起 `BusRd`，成功后若当前没有其他 cache 持有该缓存行，则变为 `E`；否则变为 `S`。写之前需要发起 `BusRdX`，成功后完成写入并变为 `M`

#### 五种原语

本地事件：**由当前核心发起**，表示当前核心想对该缓存行执行什么操作

- `PrRd` (`Processor Read`)：本核发起读请求；如果当前状态允许，则直接在本地完成读取，否则会进一步触发 `BusRd`
- `PrWr` (`Processor Write`)：本核发起写请求；如果当前状态允许，则直接在本地完成写入，否则会进一步触发 `BusRdX` 或 `BusUpgr`

 总线事务：为了完成本地事件而在一致性系统中发起的事务，其他核心会**观察到这些事务**并据此更新自己的缓存状态

- `BusRd` (`Bus Read`)：读未命中时发起的读事务，用于从**其他 cache** 或**下层内存层级**取回该缓存行
- `BusRdX` (`Bus Read Exclusive`)：写未命中时发起的独占读事务，用于从**其他 cache** 或**下层内存层级**取回该缓存行，并获得独占写权限
- `BusUpgr` (`Bus Upgrade`)：当前核心已经有该缓存行但没有写权限时发起的升级事务，只获取独占写权限，不重新取数据

#### 状态转换

不同本地状态下，发起读写请求时的典型动作如下：

| 当前状态 | 本地读 `PrRd`                                        | 本地写 `PrWr`                              |
| ---- | ------------------------------------------------- | --------------------------------------- |
| `M`  | 本地读取，状态保持 `M`                                     | 本地写入，状态保持 `M`                           |
| `E`  | 本地读取，状态保持 `E`                                     | 本地写入，状态变为 `M`                           |
| `S`  | 本地读取，状态保持 `S`                                     | 发起 `BusUpgr`，获得独占权限后完成写入，状态变为 `M`       |
| `I`  | 发起 `BusRd`，取回缓存行后若当前没有其他 cache 持有则变为 `E`，否则变为 `S` | 发起 `BusRdX`，取回缓存行并获得独占写权限后完成写入，状态变为 `M` |
****
不同状态下，收到总线事件的时响应如下:

| 当前状态 | `BusRd`             | `BusRdX`            | `BusUpgr` |
| ---- | ------------------- | ------------------- | --------- |
| `M`  | **提供最新数据**，状态变为 `S` | **提供最新数据**，状态变为 `I` | 正常情况下不会出现 |
| `E`  | 状态变为 `S`            | 状态变为 `I`            | 正常情况下不会出现 |
| `S`  | 状态保持 `S`            | 状态变为 `I`            | 状态变为 `I`  |
| `I`  | 状态保持 `I`            | 状态保持 `I`            | 状态保持 `I`  |

### Store Buffer

`Store Buffer` 是核心数据通路上的写缓冲，通常位于执行流水线与 `L1D` 之间，用来**暂存已经执行、但尚未真正写入缓存层次**的 `store`。

一条 `store` 指令经过 `Store Buffer` 时，可以粗略理解成下面几个步骤：

- `CPU` 执行 `store` 时，先把**写地址**和**写数据**放进 `Store Buffer`。
- `CPU` 后续执行 `load` 时，如果读取的是同一地址，可以先从 `Store Buffer` 中读取最新值，而**不必等数据先写回** `L1D`。
- `Store Buffer` 中的条目会在目标 `cache line` 已经位于本地 `L1D` 且具备写权限时，真正写入 `L1D`；如果该 `cache line` 还未装入，或暂时还没有写权限，就继续留在 `Store Buffer` 中等待。

这个等待过程可能包括：

- 获取目标 `cache line` 的独占或修改权限 (发送 `BusRdx` / `BusUpgr`)
- 等待该 `cache line` 被装入 `L1D`
- 等待前面的 miss 或 coherence 事务完成

因此，`store` 进入 `Store Buffer` 之后，并**不意味着该写入已经立刻落到** `L1D`，更**不意味着它已经对其他核心可见**。在 `Store Buffer` 中等待期间，这次写入通常对其他核心还不可见；但本核后续如果再读取同一地址，往往仍然可以直接从 `Store Buffer` 中获得最新值。这就是 `store-to-load forwarding`，也是“本核已经看到新值，而其他核心暂时还看不到”这种现象的来源。

`Store Buffer` 的作用，是把“指令层面的提交”和“缓存层面的实际写入”解耦开来。如果每条 `store` 都必须同步等待 `cache` 写入完成、拿到一致性协议要求的写权限后才能继续，写延迟就会直接暴露给流水线，严重影响处理器吞吐。执行 `store` 指令时，地址和值通常会先进入 `Store Buffer`，随后这条指令就可以在流水线中 `retire`。

关于指令 `retire` 的详细内容见[[流水线CPU]]。

### Invalidate Queue

`Invalidate Queue` 是核心接收失效请求时使用的缓冲，通常位于总线 (其实还要经过本地 `coherence controller`) 与 `L1 cache` 之间，用来**暂存已经到达、但尚未真正作用到本地缓存状态**的 `invalidate` 请求。这里的 `coherence controller` 可以先粗略理解成每个核心旁边负责处理一致性事务的本地控制逻辑。

一条 `invalidate` 请求经过 `Invalidate Queue` 时，可以粗略理解成下面几个步骤：

- 其他核心的写入触发一致性事务后，本核会收到对应的 `invalidate` 请求，这个请求会先进入 `Invalidate Queue`。
- `Invalidate Queue` 中的条目随后会作用到本地 `L1 cache`，把对应的 `cache line` 标记为无效，或者更新它的 coherence 状态。
- 在某些内存顺序要求下，本核后续的 `load` 不能越过这些尚未处理完成的失效请求；处理器需要确保这些失效请求不会以错误的顺序影响后续访问的可见性。

因此，`invalidate` 请求进入 `Invalidate Queue` 之后，并**不意味着本地 `cache` 已经立刻完成了失效处理**。在 `Invalidate Queue` 中等待期间，这个失效请求虽然已经到达本核，但对应的 `cache line` 可能还没有真正从本地 `cache` 中移除。不过从后续访问的角度看，这条 `cache line` 已经**不能再被当成普通有效副本直接使用**；如果新的 `load/store` 会受到这次失效的影响，硬件就必须先处理、阻塞或重试，而**不能继续直接返回旧值**。

相关表述可以参考：

> Arm Community, *Cache Coherency Fundamentals*:
> Coherency is about ensuring all processors, or bus masters in the system **see the same view of memory**.
> Hardware managed coherency offers an alternative to simplify software. With this solution any cached data marked 'shared' will always be up to date, automatically. All processors and bus masters in that sharing domain see the exact same value.

因此，`Invalidate Queue` 更适合被理解成“失效请求已经到达，但本地 `cache` 的稳定状态更新尚未完成”的微架构过渡阶段，而不是“同一地址上的缓存一致性已经放松”。这里要注意：上面的引文并没有直接逐字写出“invalidate 尚未 apply 时，后续新 `load` 一定不能读旧值”；这一步是由 coherency 的定义推出来的。既然 **coherency 要求同一共享域内的观察者看到一致的内存视图**，那么对于同一地址的**后续新 `load`**，处理器就不能因为存在 pending invalidate，就继续把本地旧副本当成合法值直接返回；否则就会在架构层面破坏缓存一致性。

> Wikipedia MESI protocol：
> a CPU can be oblivious to the fact that a cache line in its cache is actually invalid, as the invalidation queue contains invalidations that have been received but haven't yet been applied. Note that, unlike the store buffer, the CPU can't scan the invalidation queue, as that CPU and the invalidation queue are physically located on opposite sides of the cache.

Wikipedia这里个人认为可能有些误导，他说CPU可能不知道某些cache line已经实际失效，也就是失效队列中有这些cache line的失效请求。这里可能在说物理层面存在这个“失效请求已经到达，但对应cache line还没标失效“的窗口存在。这不意味着CPU后续load这些cacheline的时候会读到失效的值，因为这样就破坏了对**缓存一致性**的定义。

`Invalidate Queue` 的作用，是把“失效请求的到达”和“本地缓存状态的实际更新”解耦开来。如果每次收到 `invalidate` 请求时，都必须立刻同步修改本地 `cache` 状态并完成相关处理，那么一致性事务的延迟就会直接暴露给本核的执行流水线和缓存访问路径，影响处理器吞吐。

### 补充说明

- `x86` 采用的是 `x86-TSO` 内存模型。`TSO` 是 `Total Store Order`，可以理解成一种**总存储顺序**更强的内存模型：每个核心自己的 `store` 对外表现得像是按程序顺序进入一个较强的全局可见顺序中。对普通 cacheable memory，`x86` 硬件必须把 `store buffer`、pending invalidate 等微架构内部延迟“藏起来”，不能让它们以违反 `TSO` 的方式直接暴露给软件。
- 从效果上看，`x86-TSO` 保证的是较强的**对外可见顺序**，而不是要求微架构内部“立刻删掉某条 cache line”。对于同一地址，一旦某次写已经在架构上对其他核心可见，之后就不能再合法地返回比它更早的旧值；而一个核心自己的多个 `store`，也**对外表现得像按程序顺序可见**。
- ARM 的内存模型更弱，但这里的“弱”主要体现在**跨地址**的可见性顺序，而不是说 ARM 放弃了对同一地址的缓存一致性。对于同一地址上的后续新 `load`，ARM 也不能因为 pending invalidate 的存在，就继续把本地旧副本当成合法值直接返回。
- ARM 更容易暴露的问题，是不同地址之间的观察顺序。例如一个核心先写 `data = 1`，再写 `flag = 1`；另一个核心先读到 `flag == 1`，随后却仍读到 `data == 0`。这就是典型的**跨地址 stale read**：单个地址上的 coherence 没有被破坏，但不同地址上的可见性顺序不符合程序员直觉。

这也正是为什么在弱序架构上，需要用同步原语来约束这些跨地址的可见性顺序。

内存屏障首先是软件可见的同步原语，通常在 ISA 层体现为一条屏障指令；从硬件实现角度看，处理器需要通过约束 `store buffer`、`invalidate queue` 等内部机制来实现它的语义。可以近似理解成：在这些同步点前，**先前的写不能继续滞留**在 `store buffer` 中，而**先前收到、会影响后续可见性的失效请求也不能继续只停留**在 `invalidate queue` 这种过渡状态里；它们需要**被推进到对外可见、或至少不再影响后续观察结果的状态**。

关于内存屏障的详细内容见[[指令重排和内存屏障]]。

C++ 的**内存序**就是描述这类顺序要求的抽象之一，例如 `release/acquire` 用来建立“发布-获取”的可见性关系，防止上面这种跨地址的 stale read。

关于 C++ 内存序的详细内容见[[原子变量和内存序]]。

## 编程实践

### 各级存储结构访问用时

- `L1` 命中：`3~5 cycles`，约 `1ns`，基准 `1x`
- `L2` 命中：`10~20 cycles`，约 `3~7ns`，约 `3x~5x L1`
- `L3 / LLC` 命中：`30~70 cycles`，约 `10~25ns`，约 `2x~4x L2`
- 本地 `DRAM`：约 `300~600 cycles`，约 `100~200ns`，约 `5x~10x L3`
- 远端 `DRAM`（跨 `NUMA node`）：约 `450~900 cycles`，约 `150~300ns`，约 `1.3x~2x` 本地 `DRAM`

- 跨核读取另一核刚写过的 `cache line`：常见约 `40~100 cycles`，约 `15~35ns`，约 `1x~3x L3`
- `S -> M` 升级 / 获取写权限：常见约 `20~80 cycles`，约 `7~30ns`，约 `2x~8x L2`
- 争用同一条 `cache line` 的单次所有权转移：常见约 `50~150 cycles`，约 `20~60ns`，约 `10x~30x L1`
- 跨 `NUMA node` / 跨 socket 的所有权转移：常见约 `100~300+ cycles`，约 `40~120ns+`，约 `2x~4x` 本地跨核转移

### Cache Line Bouncing

`cache line bouncing` 指的是：多个核心**反复读写同一条** `cache line`，导致这条 `cache line` 的所有权在不同核心之间频繁转移。

这在一致性协议下通常表现为：

- 核 A 刚把某条 `cache line` 变成可写状态
- 核 B 很快又要写同一条 `cache line`
- 于是该 `cache line` 又被失效、转移到核 B
- 接着核 A 再写时，又要重新把它抢回来

如果这种来回切换非常频繁，就会出现明显的性能下降。编程里常见的例子有：

- 多个线程频繁更新同一个计数器
- 一个自旋锁所在的 `cache line` 被多个核心反复争用
- 生产者和消费者反复写同一条状态变量所在的 `cache line`

`cache line bouncing` 的核心问题，不是算术运算本身慢，而是**一致性流量和 cache line 所有权转移太频繁**。

### False Sharing

`false sharing` 指的是：多个线程虽然访问的是**不同变量**，但这些变量恰好落在**同一条 `cache line`** 中，于是硬件仍然会把它们当成同一条共享数据来维护一致性。

例如：

- 线程 A 只写 `x`
- 线程 B 只写 `y`
- 但 `x` 和 `y` 在同一条 `cache line` 上

此时即便两个线程从程序语义上没有真正共享同一个变量，硬件层面仍然会因为它们都在改同一条 `cache line`，导致这条 line 在核心之间来回 bouncing。

所以可以把两者关系理解成：

- `cache line bouncing` 是现象
- `false sharing` 是常见原因之一

### 常见症状

在实际编程里，这类问题通常会表现为：

- 线程数增加后性能反而明显下降
- CPU 使用率很高，但吞吐提升很差
- 明明每个线程都只改“自己的变量”，却仍然有强烈的多核干扰
- 加锁、原子计数、队列 head/tail 等热点字段附近出现异常高的开销

### 常见规避方式

常见做法包括：

- 给每线程私有数据做 `cache line` 对齐或填充 `padding`，例如在 C++ 中用 `alignas(64)`，避免落在同一条 `cache line` 上
- 减少多个核心对同一共享计数器的频繁写入，改成每线程局部累积再汇总

这类优化的出发点通常不是“减少指令数”，而是**减少 cache coherence 带来的所有权转移和失效流量**。
