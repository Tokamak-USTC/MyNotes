## 动态库制作流程

考虑示例程序 `main.c`，`foo.c` 和 `bar.c`

```c
// main.c
int foo(int x);

int bar(int x);

int main(void) {
  return foo(1) + bar(1);
}
```

```c
// foo.c
int baz = 0;

int foo(int x) {
  baz = 42;
  return x;
}
```

```c
// bar.c
int bar(int x) {
  return x;
}
```

这里约定：

- `foo.c` 编译为 `PIC` 目标文件，并进一步链接成动态库 `libfoo.so`
- `bar.c` 编译为普通目标文件 `bar.o`
- `main.c` 同时调用 `foo` 和 `bar`，这样后续可以直接比较“动态库函数调用”和“静态链接进主程序的函数调用”在最终产物中的差异

制作动态库及链接的流程：

1. 编译 `foo.c`

```shell
gcc -c -fPIC foo.c -o foo.pic.o
```

2. 制作动态库

```shell
gcc -shared foo.pic.o -o libfoo.so
```

3. 编译 `bar.c`

```shell
gcc -c bar.c -o bar.o
```

4. 编译 `main.c` 并链接 `libfoo.so` 和 `bar.o`

```shell
gcc main.c bar.o -L. -lfoo -o main.out
```

## 编译阶段

需要被动态链接的源文件在编译阶段就与其他源文件产生了不同。

### PIC 与 non-PIC

`PIC` 是 **Position-Independent Code**，即**位置无关代码**。

如果一个共享对象由 **position-dependent code** 构成，那么它在运行时可能需要修改 **text segment**。动态装载器需要把代码段临时映射成可写，然后把其中的可重定位引用修补成当前装载地址下的值。这样会带来几个问题：

1. `.text` 段不再只是只读代码，运行时需要被修改；
2. 被修改后的代码页会变成当前进程的私有副本，不能继续在多个进程之间共享；
3. text relocation 通常会引入更多运行时重定位工作，带来额外启动和装载开销。

而如果共享对象由 **position-independent code** 构成，可重定位引用通常会被改写成对共享对象数据段中某些表项的**间接访问**。运行时真正需要修补的是这些数据段里的表项，而不是 `.text` 里的指令本身。具体到 ELF/x86-64 上，这类间接结构主要就是 **GOT** 和 **PLT**。

`PIC` 和 non-`PIC` 的主要区别，通常不在于 ELF 结构上多了什么特殊 section，而在于：编译器对符号引用生成了**不同的寻址方式和重定位类型**，也就是后续对这些引用的**修补方式**不同。

需要注意的是，`GOT` 和 `PLT` **并不是**在 `-fPIC` **编译这一步直接生成**的；`-fPIC` 真正做的是改变 `.o` 中相关引用的代码生成方式，并留下诸如 `GOTPCREL`、`PLT32` 这类重**定位条目**，使这些位置在后续链接时能够按 `PIC` 语义被处理。至于最终是否生成 `GOT` / `PLT` 表项，以及生成哪些表项，则取决于**链接阶段**的输出类型、符号可见性和是否需要动态解析，而不是由 `-fPIC` 单独决定的。

### 具体区别

#### .text节的指令区别

只摘出真正有区别的位置来看，`foo.pic.o` 中是：

```shell
7:   48 8b 05 00 00 00 00    mov    0x0(%rip),%rax
e:   c7 00 2a 00 00 00       movl   $0x2a,(%rax)
```

`foo.o` 中则是：

```shell
7:   c7 05 00 00 00 00 2a 00 00 00    movl   $0x2a,0x0(%rip)
```

可以看到，`foo.pic.o` 则是**先取出 `baz` 的地址，再通过该地址间接写入**；而`foo.o` 是**直接通过 RIP-relative 偏移访问 `baz` 本体**。

#### 重定位条目的区别

只摘出 `.text` 里和 `baz` 对应的重定位来看，`foo.pic.o` 中是：

```shell
000000000000000a R_X86_64_REX_GOTPCRELX  baz-0x0000000000000004
```

`foo.o` 中则是：

```shell
0000000000000009 R_X86_64_PC32     baz-0x0000000000000008
```

这里 `foo.pic.o` 里的 **`R_X86_64_REX_GOTPCRELX`** 表示：该处不是直接去修补 `baz` 本体的位置，而是要按 **PC-relative** 的方式定位到 `baz` 对应的 **GOT** 表项，再通过该表项间接访问 `baz`；而 `foo.o` 里的 **`R_X86_64_PC32`** 则表示：该处直接按 **PC-relative** 方式，把对 `baz` 的引用修补到指令字段中。

因此，这个例子里 PIC 和 non-PIC 的区别不只是“重定位条目名字不同”，而是：**不同的重定位类型恰好反映了不同的指令序列和不同的符号访问方式。**

### -fPIC 的编译承诺

按 GCC 文档的说法，`-fPIC` 的编译承诺是：生成适合用于共享库的 **position-independent code**。具体到符号引用上，可以分成两类来看：

- **数据符号**：这类代码会通过 **GOT** 访问运行时才最终确定的地址，相应表项由动态装载器在程序启动时解析。
- **函数符号**：`-fPIC` 只保证调用方式满足位置无关；至于最终是否经 **PLT** 调用，则取决于该函数在链接阶段是否需要按动态可解析的 non-local 符号处理。


## 链接阶段

动态链接实现中的核心机制，如 **`PLT`** 和 **`GOT`**，正是在这一步由链接器建立起来的。

### PLT 和 GOT

使用 `objdump -d -j .plt main.out` 查看 `main.out` 的 `.plt` section，结构如下：

```shell
liyunhan.713@n37-108-145:~/projects/cpptest$ objdump -d -j .plt main.out

Disassembly of section .plt:

0000000000001020 <foo@plt-0x10>:
    1020:       ff 35 ca 2f 00 00       push   0x2fca(%rip)        # 3ff0 <_GLOBAL_OFFSET_TABLE_+0x8>
    1026:       ff 25 cc 2f 00 00       jmp    *0x2fcc(%rip)        # 3ff8 <_GLOBAL_OFFSET_TABLE_+0x10>
    102c:       0f 1f 40 00             nopl   0x0(%rax)

0000000000001030 <foo@plt>:
    1030:       ff 25 ca 2f 00 00       jmp    *0x2fca(%rip)        # 4000 <foo@Base>
    1036:       68 00 00 00 00          push   $0x0
    103b:       e9 e0 ff ff ff          jmp    1020 <_init+0x20>
```

这里可以先注意一个最直接的现象：`.plt` 中只出现了 `foo@plt`，而没有 `bar@plt`。这是因为 `foo` 来自动态库 `libfoo.so`，主程序对它的调用需要保留动态解析入口；而 `bar` 来自目标文件 `bar.o`，在链接阶段就已经把对应目标文件并入 `main.out`，因此对 `bar` 的调用通常会被直接修补成对最终地址的相对调用，而不会额外创建 `PLT` stub。

### PIC 生成共享库（.o到.so）

从 `foo.pic.o` 到 `libfoo.so`，链接器主要会按下面这个顺序工作：

1. **符号解析与重定位**
2. **节合并与输出布局**
3. **生成 GOT 和 PLT**
   对仍需要通过间接方式访问的符号，链接器会在输出文件中建立对应的 **`GOT`** 和必要时的 **`PLT`**。需要注意的是，共享库自身也可能包含一套自己的 `PLT/GOT`：当 `.so` 内部代码**引用其他共享库中的符号**，运行时会通过该 `.so` 自己的 `PLT/GOT` 完成符号解析和最终跳转。
4. **生成动态符号表与动态段**
   链接器会生成 **`.dynsym`**、**`.dynstr`** 和 **`.dynamic`** 等结构，用来记录共享库对外可见的动态符号，以及动态装载阶段所需的元数据。

#### .dynamic

`.dynamic` 可以理解为**共享库动态链接信息的总目录**。它本身并不直接存放完整的符号表或重定位表内容，而是由一组 **`DT_*`** 条目组成，用来告诉动态装载器：

- 该对象依赖哪些共享库，例如 **`DT_NEEDED`**
- 动态符号表和字符串表位于哪里，例如 **`DT_SYMTAB`**、**`DT_STRTAB`**
- 动态重定位表位于哪里，例如 **`DT_RELA`**、**`DT_JMPREL`**
- `PLT/GOT`、初始化函数、析构函数等运行时元数据位于哪里

因此，`.dynamic` 更像是“运行时该去哪里找其他动态链接结构、该按什么规则处理它们”的说明书，而不是这些结构本身。

#### .dynsym

`.dynsym` 是**动态符号表**，长的和 `.symtab` 差不多，记录运行时动态链接真正需要关注的那部分符号。它通常包括：

- 当前共享库对外可见、可能被其他对象引用的导出符号
- 当前共享库自己引用、但需要在运行时解析的外部符号

它的单个表项和 `.symtab` 一样，本质上都是 `Elf64_Sym`；区别主要在于：`.dynsym` 是为动态装载器准备的、规模更精简的符号表，而 `.symtab` 则通常更完整，包含更多只对静态链接、调试和分析有用的符号。

5. **生成动态重定位表**
   对仍需要在装载时继续修补的位置，链接器会生成输出文件中的动态重定位表，例如 **`.rela.dyn`** 和 **`.rela.plt`**。这些表项描述了后续动态装载器应如何完成最终地址修补和符号绑定
6. **输出共享对象文件**
   最终得到的产物是一个 ELF 共享对象文件，其 ELF 类型通常为 **`ET_DYN`**。到这一步为止，链接器已经把输入的 `PIC` 目标文件组织成一个可以被后续动态装载器继续处理的 `.so`。
