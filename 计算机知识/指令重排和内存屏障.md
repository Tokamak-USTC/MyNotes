## 概览

## 指令重排

### 指令重排的语义

指令重排首先是一种**现象** / **观察到的结果**，而不是单一原因。它描述的是：程序明明按 `A -> B` 的顺序书写，但在**架构可观察结果** / **多线程程序执行结果**上，这两个操作的效果却可能像是按另一种顺序发生了。

这里要特别注意，指令重排并**不一定**意味着某个核心真的把两条指令**按相反顺序执行**了。造成这种现象的原因可能是：

- 编译器在生成机器指令时改了顺序
- CPU 内部发生了乱序发射、乱序执行、乱序完成
- 前面的写入虽然已经退休，但还没有对其他核心**全局可见**

硬件视角下通常表现为：**其他核心/线程观察到的内存访问顺序**与程序顺序不一致。

软件视角下通常表现为：**多线程程序**的**执行结果不符合预期**，**好像**某些**指令的执行顺序反过来**一样。

### 四种重排类型

按**程序顺序中的前后两类内存操作**来分，最常见的重排现象可以分成 `Load->Load`，`Store->Store`，`Load->Store`，`Store->Load`。

#### Load→Load 重排

程序顺序里先读 `A`、再读 `B`，但从效果上看，后一个 `load` 好像先发生。典型影响是：本来希望“先看到数据结构的状态 A，再看到状态 B”，结果观察顺序反了。

```cpp
int data = 0;
std::atomic<bool> flag = false;

// Writer
data = 42;
flag.store(true, std::memory_order_release);

// Reader
while(!flag.load(std::memory_order_relaxed));
assert(data == 42);

// data is expected to be 42, but it may still be 0.
```

这个例子演示了 Load->Load 重排的效果。实现程序在x86上没问题，arm上会中断言。（apple M4桑跑出来了）。

#### Store→Store 重排

程序顺序里先写 `A`、再写 `B`，但其他核心可能先观察到 `B` 的新值，再观察到 `A` 的新值。典型例子是“先写数据，再写标志位”，结果别的核心先看见标志位，后看见数据。

```cpp
int data = 0;
std::atomic<bool> flag = false;

// Writer
data = 42;
flag.store(true, std::memory_order_relaxed);

// Reader
while(!flag.load(std::memory_order_acquire));
assert(data == 42);

// data is expected to be 42, but it may still be 0.
```

这个例子演示了 Store->Store 重排的效果。实现程序在x86上没问题，arm上会中断言。（但是我在apple M4上没跑出来）。

#### Load→Store 重排

程序顺序里先读 `A`、再写 `B`，但对外效果上后面的 `store` 好像先发生。典型影响是：本来想先根据某个共享状态做判断，再发布新的写入，但别的核心可能更早看到后面的写。

```cpp
std::atomic<int> x = 0;
std::atomic<int> y = 0;

int r0 = -1;
int r1 = -1;

// Thread 0
r0 = y.load(std::memory_order_relaxed); // A
x.store(1, std::memory_order_relaxed);  // B

// Thread 1
r1 = x.load(std::memory_order_relaxed); // C
y.store(1, std::memory_order_relaxed);  // D

// One might expect at least one load to see 0,
// but it is possible for both r0 and r1 to be 1.
```

这个例子中，假设没有发生指令重排，可能的执行顺序有如下几种：

1. **A -> B -> C -> D**，此时结果应该是 `r0 = 0, x = 1, r1 = 1, y = 1`
2. **A -> C -> B -> D**，此时结果应该是 `r0 = 0, x = 1, r1 = 0, y = 1`
3. **A -> C -> D -> B**，此时结果应该是 `r0 = 0, x = 1, r1 = 0, y = 1`
4. **C -> A -> B -> D**，此时结果应该是 `r0 = 0, x = 1, r1 = 0, y = 1`
5. **C -> A -> D -> B**，此时结果应该是 `r0 = 0, x = 1, r1 = 0, y = 1`
6. **C -> D -> A -> B**，此时结果应该是 `r0 = 1, x = 1, r1 = 0, y = 1`

也就是说，在**每个线程内部都保持 `load -> store` 程序顺序**的前提下，结果只可能是：

- `r0 = 0, r1 = 1`
- `r0 = 0, r1 = 0`
- `r0 = 1, r1 = 0`

**不会出现 `r0 = 1, r1 = 1`。** 如果出现 `r0 = 1, r1 = 1` 就说明至少有一侧发生了 **Store→Load 重排**（apple M4上没跑出来）。

#### Store→Load 重排

程序顺序里先写 `A`、再读 `B`，但前面的 `store` 还没有对外**全局可见**时，后面的 `load` 已经完成。这通常是最容易在讨论内存屏障时单独拿出来强调的一类，因为它最能体现“本核内部已经往后走了，但前面的写还没有真正对外建立顺序”。

```cpp
std::atomic<int> x = 0;
std::atomic<int> y = 0;

int r0 = -1;
int r1 = -1;

// Thread 0
x.store(1, std::memory_order_relaxed);  // A
r0 = y.load(std::memory_order_relaxed); // B

// Thread 1
y.store(1, std::memory_order_relaxed);  // C
r1 = x.load(std::memory_order_relaxed); // D

// One might expect at least one load to see 1,
// but it is possible for both r0 and r1 to be 0.
```

这个例子中，假设没有发生指令重排，可能的执行顺序有如下几种：

1. **A -> B -> C -> D**，此时结果应该是 `r0 = 0, x = 1, r1 = 1, y = 1`
2. **A -> C -> B -> D**，此时结果应该是 `r0 = 1, x = 1, r1 = 1, y = 1`
3. **A -> C -> D -> B**，此时结果应该是 `r0 = 1, x = 1, r1 = 1, y = 1`
4. **C -> A -> B -> D**，此时结果应该是 `r0 = 1, x = 1, r1 = 1, y = 1`
5. **C -> A -> D -> B**，此时结果应该是 `r0 = 1, x = 1, r1 = 1, y = 1`
6. **C -> D -> A -> B**，此时结果应该是 `r0 = 1, x = 1, r1 = 0, y = 1`

也就是说，在**每个线程内部都保持 `store -> load` 程序顺序**的前提下，结果只可能是：

- `r0 = 0, r1 = 1`
- `r0 = 1, r1 = 1`
- `r0 = 1, r1 = 0`

**不会出现 `r0 = 0, r1 = 0`。** 如果出现 `r0 = 0, r1 = 0`，就说明至少有一侧发生了 **Store→Load 重排**（x86开发机跑出来了）。

#### 补充说明

不同架构允许暴露出来的重排类型并不一样：

- 对普通 **`x86-TSO` 的 `WB` 内存**，架构层面通常只允许 **Store→Load 重排** 暴露出来，另外三类一般会被维持住。
- 对 **ARM 这类弱内存模型**，如果没有屏障、`acquire/release` 或更强同步约束，**四种类型**都可能出现。

### 导致原因

可以把重排现象的来源分成三层来理解：**编译层、执行层、可见性层**。

#### 编译层

编译器为了优化性能，可能在不改变**单线程语义**的前提下调整指令顺序。这种调整属于**编译期重排**。

- 约束条件是 `as-if-serial`：只要**单线程可观察行为不变**，编译器就可以改写指令次序。
- 一个很简单的例子是：如果两条语句之间**没有数据依赖**，编译器就可能交换它们的先后顺序；或者把一个纯寄存器计算提前到一次访存之前，只要这样做不会改变单线程最终结果。

关于编译器对指令的影响，见[[编译优化]]。

#### 执行层

即使编译器没有改顺序，处理器在运行时也可能为了提高吞吐做**乱序执行**。这一层更准确地说，是**处理器内部处理顺序乱了**。

- **乱序发射**：指令会 **按照顺序** 进入发射队列，然后等待 **操作数就绪** 和 **执行单元空闲**，这种情况下，后来的指令可能先满足发射条件，就会先被发射到执行单元去。也就是说指令是按序进入发射队列的，但是可能乱序离开，而不是FIFO。
- **乱序执行**：后面的**短延迟指令先执行完**，前面的**长延迟指令后完成**。比如浮点运算指令比整型运算指令多几个周期，所以即使先发射到执行单元也可能在整型运算指令之后完成。

这些现象能出现，是因为现代 CPU 有**流水线、寄存器重命名、保留站、调度队列、重排序缓冲区（ROB）和多个执行单元**。它不会机械地等“前一条彻底做完再做下一条”，而是会优先处理**已经就绪且不冲突**的指令。

现代 OoO CPU 一般仍然**按序退休**，以保证精确异常、错误恢复和可回滚性。对 `store` 来说，写入真正对其他核/线程可见通常还发生在**退休之后**：指令退休后，数据往往还要先停留在 `store buffer` 中，之后才逐步写入 cache 并通过一致性协议对外传播。因此，**乱序发射/执行主要改变的是本核内部处理顺序，本身通常不是内存可见性层面重排的直接原因**；后者更多来自 `store buffer`、访存队列和 cache coherence 的传播时序。

关于指令的生命周期（**发射、完成、退休**等），见[[流水线CPU]]。

#### 可见性层

即使编译器没有改顺序、CPU 内部也不一定真的把两条操作交换执行，其他核/线程看到的内存更新顺序仍然可能和程序顺序不同。更准确地说，这一层关注的是**写入什么时候对别的核可见**。

- **`store buffer` 导致的延迟可见**：本核执行 `store` 后，数据可能先进入 **`store buffer`**，暂时还没有对其他核**全局可见**。典型场景是程序顺序上先 `store A` 再 `load B`，但 `store A` 还留在 buffer 中时，后面对不同地址的 `load B` 已经完成；这说明本核后续的 `load` 可以先于前面的 `store` **全局可见**，这正是典型的 **Store→Load 重排** 场景。（注意是**全局可见**而不是**指令完成**。这个场景指令完成的顺序是按序完成的）
- **cache 一致性传播延迟**：某个核已经完成写入，但这个写入变成“其他核也能看见”的状态还需要经历**一致性消息传播**。典型场景是核 0 先写标志位前的数据，再写标志位；如果相关 `cache line` 的传播时间不同，核 1 可能先看到**标志位更新**，后看到**真实数据**。这类跨地址可见性失配在 **ARM 等弱内存模型**下更典型；对普通 **x86-TSO 的 WB 内存**，架构层面通常不会这样暴露。
- **invalidate / acknowledgment 时序差异**：在基于失效的一致性协议里，一个写操作要让其他核上的旧副本失效，但不同核收到失效、处理失效、返回确认的时间并不完全一致。典型场景是写入已经在本核提交，但其他核对旧 `cache line` 的失效处理存在**时间差**，于是不同核短时间内对同一组写入的**观察顺序可能不同**。

这一层严格来说不一定是“执行顺序真的被重排”，而是：**全局可见顺序发生了变化，看起来像被重排了一样**。

关于**缓存一致性协议和一致性传播**，见[[高速缓存]]。

## 内存屏障

### 内存屏障的语义

可以理解为在**某个cpu**的访问队列中**划出条线**，**特定类型**的**访存**指令**不能跨过**这条线。注意，这个也说的是**其他核心或设备观察到的结果**。

内存屏障只有在**核心之间交互** / **核心和设备之间交互**时才才有用，即其他核心 / 设备要观察某个核心的指令执行结果时。如果只考虑**单核行为没必要使用内存屏障**。

### 几种内存屏障原语

Linux 提供了下面几种内存屏障原语：

- **read barrier**（ `smp_rmb()` ）: **双向读屏障**，屏障前的 `load` 不能**被观察到**跑到屏障后，屏障后的 `load` 不能**被观察到**跑到屏障前
- **write barrier**（ `smp_wmb()` ）：**双向写屏障**，屏障前的 `store` 不能**被观察到**跑到屏障后，屏障后的 `store` 不能**被观察到**跑到屏障前
- **general barrier**（ `smp_mb()` ）：**全屏障**，屏障前的 `load` / `store` 不能**被观察到**跑到屏障后，屏障后的 `load` / `store` 不能**被观察到**跑到屏障前

还有一些隐式的内存屏障：

- **acquire**（ `smp_load_acquire()` / `spin_lock()` ）：**单向屏障**，屏障**前**的 `load` / `store` 不能**被观察到**跑到屏障**后**
- **release**（ `smp_store_release()` / `spin_unlock()` ）：**单向屏障**，屏障**后**的 `load` / `store` 不能**被观察到**跑到屏障**前**

以 x86 的某些 Linux 实现为例，内存屏障原语常会同时包含编译器约束（如 `memory clobber` ）和显式的 CPU 层屏障指令（如 `mfence` / `lock` 前缀指令等 ）。

```c
#define __smp_mb()	asm volatile("lock addl $0,-4(%%" _ASM_SP ")" ::: "memory", "cc")

//x86_64展开
#define __smp_mb()	asm volatile("lock addl $0,-4(%%rsp)" ::: "memory", "cc")
```

关于 `volatile` 的含义和用法，见[[volatile关键字]]。

### 编译器屏障

**编译器屏障（compiler barrier）约束的是编译器优化器，而不是 CPU 本身。** 它告诉编译器：**不要把屏障前后的内存访问跨屏障重排**。

常见的例子有：

- GCC/Clang 中常见的 `asm volatile("" ::: "memory")`，它几乎不做实际计算，但会告诉编译器：**这里前后的内存访问顺序不要乱动**。这条指令可能会改内存，如果跨过这条指令来重排访存指令，可能读到错误的结果。
- 标准 C++ 中更接近这一语义的是 `std::atomic_signal_fence()`，它主要约束编译器，而不要求一定生成真正的硬件 `fence` 指令。

Linux 对编译器屏障的实现：

```c
# define barrier() __asm__ __volatile__("": : :"memory")
```

### CPU内存屏障（屏障指令）

CPU 层的内存屏障通常体现为 **ISA 相关的显式屏障指令**。不同架构的名字不一样，但作用本质上都是：在运行时约束 CPU 和内存系统，不让某些 `load/store` 或后续执行跨过这个顺序点。

常见例子有：

- **x86**：`lfence`、`sfence`、`mfence`
  - `lfence`：偏读侧屏障。可以粗略理解为：前面的 `load` 要在 `lfence` 完成前取得数据，后续指令不能在 `lfence` 完成前开始执行。
  - `sfence`：偏写侧屏障。主要用于约束前面的写入顺序和可见性建立。
  - `mfence`：全屏障，读写两边都管。
  - `lock` 前缀指令（如 `lock xchg`、`lock addl`、`lock cmpxchg`）：它们首先是**原子读-改-写指令**，不是单独的一条传统 fence 指令；但在 x86 上通常可视为具有 **full barrier 效果**，因此在很多同步原语实现里也会顺便承担屏障作用。
- **ARM / AArch64**：`DMB`、`DSB`、`ISB`
  - `DMB`：最常见的数据内存屏障
  - `DSB`：比 `DMB` 更强，要求前面的访问完成后再继续
  - `ISB`：主要是指令流同步，不是普通数据内存顺序屏障

这里要注意：**不是所有顺序约束都一定要靠一条单独写出来的 fence 指令实现。** 有些架构上，某些原子操作、**锁指令**或带 `acquire/release` 语义的访存，本身就可能顺便提供一部分屏障效果。
