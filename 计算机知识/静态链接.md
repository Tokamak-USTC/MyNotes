## 静态链接时发生了什么

### 静态链接的输入

考虑这样一个程序 `main.c`，包含两个已经定义的函数 `bar`、`main`，一个未定义的函数 `foo`，一个外部全局变量 `baz`：

```c
// main.c
int foo(int x, int y);

int bar(int x, int y) { return x + y; }

static int local(int x, int y) { return x + y; }

extern int baz;

int main() {
  int a = 1, b = 2;
  int c = foo(a, b);
  int d = bar(a, b);
  int e = local(a, b);
  baz = 42;
  return 0;
}
```

`call` 指令的机器码里存的是**rel32偏移**，反汇编里显示的通常是**解算后的目标地址**。因此，`e8 xx xx xx xx` 中的 `xx xx xx xx` 表示一个**相对于下一条指令地址（RIP-relative 计算基准地址）的 32 位偏移**，并采用**小端**表示，即**低有效字节在前**。

对 `baz` 进行赋值的位置是：

```shell
74:	c7 05 00 00 00 00 2a 	movl   $0x2a,0x0(%rip)        # 7e <main+0x56>
7b:	00 00 00
```

`movl` 指令的机器码里同时包含一个 **disp32偏移** 和一个 **32位立即数**。其中，`0x0(%rip)` 里的 `0x0` 表示一个**相对于下一条指令地址的 32 位偏移**。`2a 00 00 00` 就是那个立即数 `42`。

可以看到这些位置有些使用 `00 00 00 00` 进行占位，有些放进了具体的偏移量。

- 对于**外部定义**的符号，当前 `.o` 里本来就不知道它最终会落到哪里，因此只能先占位，再由链接器去别的目标文件或库里找到定义后修补。
- 对于**内部定义**的符号，其实按理说是能算出来他的定义和调用点之间的偏移的。但是**有了偏移并不意味着不需要重定位**。
  - 如果目标符号虽然在当前 `.o` 里有定义，但它是 **`STB_GLOBAL`** 或 **`STB_WEAK`** 这类 **non-local** 符号，那么这里常常仍会保留重定位，等到链接阶段做完**符号解析**，再用**最终确定的符号**来做重定位。
    - 例如，如果 `main.o` 定义了一个全局 `foo` 并在本文件里调用它，`dep.o` 也定义了一个全局 `foo` 并在本文件里调用它，那么如果两个 `.o` 都在汇编阶段把调用直接算死，就会变成“各用各的 `foo`”；但真实的 ELF 链接并不是这样，链接器会先做全局**符号解析**，而两个强全局定义通常会直接报**重复定义**错误。
  - 如果目标符号不需要给其他文件使用，比如 `static` 函数，它通常对应 **`STB_LOCAL`**，不参与外部符号解析；这时如果相对位置也已知，汇编器往往就会直接把偏移算出来。
    - 例如，示例程序中的静态函数 `local`，其偏移 `a3 ff ff ff`（小端表示的 `0xffffffa3`，即 `-0x5d`）已经被计算出来并填到对应 `call` 指令中。

## 符号解析

### 符号

符号可以理解为：**目标文件**里那些**会进入符号表、需要被链接器识别和处理**的名字或实体，如**函数**、**全局变量**、**文件内静态函数**、**静态变量**等。

不是这里所说的**符号**的，通常有：**局部变量**、已经在编译/汇编阶段被直接算掉的**常量**、**临时值**、纯粹的**局部偏移**。

每个符号由一个符号表项表示。他需要记录一个符号的**名字**、**值**、**大小**、**类型**、**绑定属性**、**可见性**以及它**关联的 section**。

符号表项的结构如下：

```c
typedef struct elf64_sym {
  Elf64_Word st_name;		/* Symbol name, index in string tbl */
  unsigned char	st_info;	/* Type and binding attributes */
  unsigned char	st_other;	/* No defined meaning, 0 */
  Elf64_Half st_shndx;		/* Associated section index */
  Elf64_Addr st_value;		/* Value of the symbol */
  Elf64_Xword st_size;		/* Associated symbol size */
} Elf64_Sym;
```

- **`st_name`**：符号名在字符串表中的**索引**（以字节为单位的偏移，往后连续读，读到 \0 结束），本身不是字符串
- **`st_info`**：同时编码了符号的**类型**和**绑定属性**
  - 编码方式：`st_info` 是一个字节，**高 4 位**表示绑定属性（bind），**低 4 位**表示类型（type）
  - 类型：回答“这个符号是什么”
	- `STT_NOTYPE = 0`：未指定具体类型
    - `STT_OBJECT = 1`：数据对象，比如全局变量、静态变量
    - `STT_FUNC = 2`：函数
    - `STT_SECTION = 3`：一个 section
    - `STT_FILE = 4`：一个源文件
  - 绑定属性：回答“它以什么身份参与链接”
    - `STB_LOCAL = 0`：局部符号，只在当前目标文件内部可见
    - `STB_GLOBAL = 1`：全局符号，可被其他目标文件引用
    - `STB_WEAK = 2`：弱符号，解析优先级低于全局符号
- **`st_other`**：额外属性；实际最重要的是符号**可见性**
- **`st_shndx`**：符号关联的 **section 索引**
  - 普通数值：表示它位于 Section Header Table 里的第 `st_shndx` 个section
  - **特殊值**：不再表示普通 section 下标，而是带有额外语义
    - **`SHN_UNDEF`**：该符号在当前 `.o` 中**只有引用**、**没有定义**，后续需要链接器去**其他目标文件**或库中**寻找定义**
    - **`SHN_ABS`**：绝对符号，不随重定位改变
    - **`SHN_COMMON`**：common symbol，常见于旧式未初始化全局变量的j表示
- **`st_value`**：该符号在其所属 **section 内的偏移量**，以字节为单位
- **`st_size`**：符号的**大小**，以字节为单位；函数可理解为**代码范围**，变量可理解为对象大小

### 符号解析过程

符号解析的核心任务，是把需要跨目标文件处理的**符号引用**，和某个具体的**符号定义**对应起来。

具体过程大致如下：

1. 链接器读取所有输入文件中的符号表，区分哪些是**定义**，哪些是**未定义引用**
  - 链接器靠**重定位表**来知道：**哪个地方引用了符号**，**引用了哪个符号**
1. 对每个未定义的 non-local 符号，在全局范围内寻找合适的定义，并按 **`STB_GLOBAL`**、**`STB_WEAK`** 等规则处理冲突
2. 如果找不到定义，就报 **undefined reference**；如果出现多个不允许并存的**强定义**，就报**重复定义**
3. 对静态库 `.a`，链接器通常按命令行顺序按需抽取成员，而不是一开始就把整个库全部并入
4. 解析完成后，链接器就知道“每个引用最终对应哪个定义”，后续再结合 section 布局和地址分配结果去做**重定位**

## 节合并与输出布局

进入这一步之前，链接器手里已经有了：所有输入 `.o` 的 **section**、**符号表**、**重定位表**，以及前面完成的**符号解析结果**。也就是说，此时链接器已经知道“每个引用最终对应哪个定义”，但这些信息仍然大多停留在各个输入文件自己的局部坐标系里。

接下来，链接器主要要完成几类工作：

1. **合并 section**：把多个输入文件中的同类 section 归并到对应的 output section 中，并决定每个 input section 在 output section 里的放置位置。
2. **换算符号坐标**：根据前面已经完成的符号解析结果，重新组织输出侧的符号信息，把很多符号的 `st_shndx` 改到对应的 output section，把 `st_value` 从“相对 input section 的偏移”换算成“相对 output section 的偏移”。
3. **整理重定位信息**：扫描 / 分析输入 `.rel.*` / `.rela.*` 这类**重定位表**，把每条重定位项从输入文件坐标系映射到输出布局坐标系，同时让它重新对应到正确的最终符号结果上。
	- **换算修补位置**：把输入重定位项里的 `r_offset` 从**相对于输入 section 的偏移**换算为**相对于 output section 的偏移**，大致类似 `output_section_offset = input_section_offset_in_output + r_offset`。
	- **索引正确符号**：根据重定位项里的 `r_info`，回到**输入符号表**中找到它引用的是**哪个输入符号**，再把这个引用**关联到**前面已经**解析好的最终符号结果**上。也就是说，真正参与后续修补的，不再是“某个 `.o` 里第几个符号表项”这种局部编号，而是它最终关联到的符号。
4. **生成 segment**：在 output section 的组织和布局逐渐明确之后，链接器还会进一步生成 **Program Header Table**，并把这些 output section 按装载属性组织成若干 **segment**。关于 `Program Header Table` 和 `segment` 的详细内容，见[[ELF]]。

这一步结束之后，链接器会得到：已经组织好的**输出 section**、扫描并整理过的**重定位信息**、已经换算好的**符号位置**、以及已经对齐到输出布局上的**修补位置**。与此同时，面向装载视角的 **segment / Program Header** 也会在输出文件成形过程中逐步建立起来；而输入 `.o` 中的静态重定位条目，则会在后续真正修补代码/数据时被逐步**消费**。

## 重定位

### 重定位的原因

如前所述，编译器是按源文件分别编译的。如果某个源文件**引用了自己没有定义的符号**，或者虽然引用的是当前文件中定义的符号，但该引用仍需要保留给链接器按最终**符号解析结果**处理，那么在编译 / 汇编阶段，就无法把指令或数据中的相关字段直接写成最终值，只能先留下 `00 00 00 00` 这类**占位字段**。

重定位要做的，就是在链接阶段根据**符号解析结果**，计算出这些位置最终该写入的值，并把**占位字段**修补成正确内容。

### 重定位条目

重定位条目在**编译**时产生。当编译器遇到一个编译时确定不了**位置** / **偏移**的符号时，就会留下一个重定位条目，以便后续进行重定位修复。

**重定位条目是符号引用和符号定义之间的关键桥梁**。他描述了何处引用了符号，以及引用了什么符号。而程序的实际内容，如 `.text`，`.data` 等中并不包含这些信息。

重定位条目的结构如下：

```c
typedef struct elf64_rel {
  Elf64_Addr r_offset;	/* Location at which to apply the action */
  Elf64_Xword r_info;	/* index and type of relocation */
} Elf64_Rel;

typedef struct elf64_rela {
  Elf64_Addr r_offset;	/* Location at which to apply the action */
  Elf64_Xword r_info;	/* index and type of relocation */
  Elf64_Sxword r_addend;	/* Constant addend used to compute value */
} Elf64_Rela;
```

- **`r_offset`**：重定位要作用的位置。
  - 对可重定位目标文件 `.o` 来说，它通常表示某个 **section 内的偏移量**，以**字节**为单位，而且**一般并不会指向指令开始的位置**，而是指令的中间的某个位置
  - 链接器后面要去对应 section 的这个位置上做修补，具体是哪个 section 取决于**该条目所在的重定位表**。比如 `.rela.text` 就对应 `.text` section
- **`r_info`**：同时编码了**目标符号索引**和**重定位类型**
  - 符号索引：对应符号在**符号表里的下标**
  - 重定位类型：指出这次修补该按什么规则计算，比如是普通的 **PC-relative** 修补，还是和 **PLT** 相关的修补；同时它也决定要修补的是一个**多宽的字段**，例如是 **4 字节** 还是 **8 字节**
    - 例如 **`R_X86_64_PLT32`**，常见于 `call foo` 这类函数调用，它通常对应修补一个 **4 字节** 的 `rel32` 字段
    - 再比如 **`R_X86_64_64`**，则通常表示要写入一个 **8 字节** 的值
- **`r_addend`**：计算重定位结果时额外带上的一个**常量加数**。在 `Elf64_Rela` 里它被显式存放在表项中；而 `Elf64_Rel` 则没有这个字段，加数通常隐含在被修补的位置里
  - 对 `call rel32` 这类 **PC / RIP-relative** 重定位来说，`r_addend` 常常用来补上“相对的是**下一条指令地址**而不是当前字段位置”这类指令语义差异。

所以，一条重定位项本质上是在说：**“到这个位置，按这种重定位类型，结合这个符号和这个加数，重新算出该写入的值。”**

### 重定位表

重定位表是由重定位条目连续排列成的数组结构，通常和某个**被修补的 section** 对应。比如 **`.rela.text`** 里的条目描述的是对 **`.text`** 中某些位置的修补，**`.rela.data`** 则对应对 **`.data`** 中某些位置的修补。

### 重定位过程

重定位时，链接器会根据**重定位类型**对应的公式，结合**目标符号的值**、**修补位置**和**加数**，算出最终应该写回去的内容。以 ELF/x86-64 常见记号来说：

- `result`：被填入 `e8` 后四个字节的值，即从RIP开始的跳转偏移
- **`S`**：目标符号的地址，由 `st_shndx` 和 `st_value` 可以确定
- **`A`**：加数，也就是 `r_addend`
- **`P`**：**被修补位置**的地址

`call rel32` 常见的 **`R_X86_64_PLT32`** / **`R_X86_64_PC32`**，就可以近似理解为：

```text
result = S + A - P
```

那么这个 `A`，也就是 `r_addend` 是从哪里来的？还是回到示例程序 `main.o`，使用 `objdump -r` 查看其重定位条目：

```shell
liyunhan.713@n37-108-145:~/projects/cpptest$ objdump -r main.o

main.o:     file format elf64-x86-64

RELOCATION RECORDS FOR [.text]:
OFFSET           TYPE              VALUE
0000000000000049 R_X86_64_PLT32    foo-0x0000000000000004
000000000000005b R_X86_64_PLT32    bar-0x0000000000000004
0000000000000076 R_X86_64_PC32     baz-0x0000000000000008
...
```

以第一条 `foo` 举例，这里的 `foo-0x4` 就表示：这条重定位引用的目标符号是 `foo`，而它的 **addend 是 `-4`**。

原因如下：
- ELF 重定位公式里的 `P`，通常取的是**被修补位置本身的地址**。
- 公式中的 `result`，即`call rel32` 指令里被修补的那个 4 字节字段，表示的是“**目标地址相对于下一条指令地址（执行到call指令时的RIP）的偏移**。
- 下一条指令的地址是 `P + 4`，所以有：`S = (P + 4) + result`，即 `result = S + (-4) -P`
- 所以得到 `A = -4`，即 `r_addend = -4`。

所以，`foo-4` 不是在说“把 `foo` 往前挪 4 字节”，而是在说：**为了匹配 `call rel32` 以“下一条指令地址”为基准的编码语义，这条重定位在计算时要额外减去 4。**

再把它和最终链接后的反汇编对应起来看：

```shell
1171:	e8 38 00 00 00       	call   11ae <foo>
```

这里：

- `S = 0x11ae`，也就是 `foo` 的地址
- `P = 0x1172`，也就是 `e8` 后面那个 4 字节 `rel32` 字段本身的地址
- `A = -4`

代入公式：

```text
result = S + A - P
       = 0x11ae - 0x4 - 0x1172
       = 0x38
```

所以最终写回去的就是 `0x38`，按小端编码后就是 `38 00 00 00`。这也正好说明：`call` 真正使用的基准地址是下一条指令 `0x1176`，因为 `0x1176 + 0x38 = 0x11ae`。
