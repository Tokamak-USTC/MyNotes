## 速览

- ELF 结构为 `ELF Header` `Program Header Table` `ELF Data` `Section Header Table`
- `Program Header` 是segment的索引，segment决定进程加载的内存视图，`.o` 文件没有这部分
- `Section Header` 是section的索引，section决定ELF文件有实际语义的信息布局，如 `.text` `.data`

## ELF 是什么

ELF 是 `Executable and Linkable Format` 的缩写。它是一种二进制对象文件格式，更准确地说，是 Unix/Linux 系统里常见的目标文件与可执行映像格式。

常见的 ELF 文件包括**可执行文件**、**共享库（共享对象）**、**可重定位目标文件 `(.o)`**，以及 **core dump 文件**。也就是说，ELF 并不只等于“可执行程序格式”，而是覆盖了链接产物、运行产物和调试转储的一整类统一格式。

名字里既有 `Executable` 又有 `Linkable`，不是因为同一个文件一定同时承担“链接”和“执行”两种角色，而是因为这套格式同时服务于链接阶段和执行/加载阶段。例如 `ET_REL` 更偏向 linkable，而 `ET_EXEC`、`ET_DYN` 更偏向 executable / loadable；它们共享同一个 ELF 格式家族。

## 理解 ELF 的两个视角：section 与 segment

理解 ELF 时，一个最关键的切分方式是区分 `section` 视角和 `segment` 视角。前者更偏向链接、调试和静态分析，后者更偏向加载和运行时映射。

`segment` 则可以理解为“按**加载需求**组织文件内容”的方式。**加载器**更关心哪些字节需要被映射到内存、映射到什么**虚拟地址**、具有什么**权限**，因此它主要通过 `Program Header Table` 来理解 ELF。尤其是 `PT_LOAD` 这样的 segment，**会直接决定程序运行时内存映像的大致布局**。

`section` 可以理解为“按**语义**组织文件内容”的方式。像 `.text`、`.rodata`、`.data`、`.bss`、`.symtab` 这样的 section，都在描述“这部分内容在程序或工具链语义上是什么意思”。因此，section 不只是给**链接器**看的，也常常是**调试器**、**反汇编器**和各种**静态分析工具**理解 ELF 的主要入口。

`section` 和 `segment` 往往不是两份独立的数据，而是同一份 ELF 内容 （`EFL Data`）的两种组织方式， 或者说是两种不同的“视图”：`section` 更偏语义分类，`segment` 更偏加载组织。

## ELF 的主要类型总览

从 `e_type` 的角度看，常见 ELF 主要可以分成四类：`ET_REL`、`ET_EXEC`、`ET_DYN` 和 `ET_CORE`。这几个类型虽然共享 ELF 这套总体格式，但用途和阅读重点并不相同。

- `ET_REL`：**可重定位目标文件**，典型例子是 `.o` 主要作为链接阶段的输入。
- `ET_EXEC`：**传统可执行文件**，通常对应非 PIE 的主程序。
- `ET_DYN`：**动态共享对象**，`.so`，也常用于现代 PIE 可执行文件。
- `ET_CORE`：**core dump** 文件，用于保存程序崩溃时的内存和状态现场。

其中，`ET_REL` 更适合从链接视角理解，`ET_DYN` 更适合从运行和加载视角理解；`ET_EXEC` 在现代系统里更多作为对比项出现，而 `ET_CORE` 则主要和调试相关。

## ET_REL：链接视角下的 ELF

`.o` 文件通常是 `ET_REL`，也就是可重定位文件。它还不能直接作为一个完整程序运行，因为其中的很多信息还没有最终确定，例如**外部符号**的具体实现、符号地址，以及某些代码和数据最终会被放到哪里。

`.o` 文件没有执行的需求，不需要被加载进内存，所以不需要segment视图，但是已经包含了许多信息，比如函数的汇编代码，一些全局变量的值，或者是符号表之类的信息，所以需要section的视图。

**ET_REL 类型的 ELF 只有 Section Header Table, 没有 Program Header Table**

关于 `.o` 文件如何进行静态链接，见[[静态链接]]。

## ET_DYN：运行视角下最常见的 ELF

`PIE` （Place Independent Executable， 现在的常见程序都是PIE）和 `.so` 都是 ET_DYN类型的ELF。

`ET_DYN` 的关键特征不是“它一定是共享库”，而是它的**装载位置通常不是在链接时就完全固定死的**，而是在**加载时动态决定的**。更具体地说，这类 ELF 往往会在加载时决定实际基址，然后再结合文件中的虚拟地址信息得到运行时地址。因此，`p_vaddr` 仍然有意义，但它通常不是单独决定最终运行地址的唯一因素，实际地址更接近 `runtime_addr = load_bias + p_vaddr` 这样的形式。

这也解释了为什么共享库通常是 `ET_DYN`。共享库需要在进程启动或运行过程中被装载到某个合适的基址上，具体基址会受到加载器决策、地址空间占用情况以及 ASLR 等制影响，因此它天然适合用 `ET_DYN` 这种“运行时再决定装载基址”的方式来表示。

关于 `.so` 文件如何进行动态链接，见[[动态链接]]。

现代 PIE 可执行文件通常也是 `ET_DYN`，原因和共享库类似。虽然它们的角色是“主程序”，不是“共享库”，但它们同样希望在加载时再决定实际装载基址，而不是像传统 `ET_EXEC` 那样更接近固定地址映像。这样主程序也能参与 ASLR，从而获得更好的地址随机化效果。

关于 `PIE` 如何进行加载 / 执行，见[[进程加载]]。

**ET_DYN 类型的 ELF 可以粗略分成四部分，从前到后分别是ELF Header，Program Header Table，ELF Data（实际内容），Section Header Table。**

## ET_EXEC 与 ET_CORE：补充说明

`ET_EXEC` 通常可以理解为传统可执行文件类型。在这种 ELF 里，段的虚拟地址通常在链接时就已经基本确定。**对 Linux 的典型主程序加载路径来说，它的有效 `load bias` 通常可以近似看成 `0`，因此运行时地址更接近直接由 `p_vaddr` 决定。**

`ET_CORE` 用于保存程序崩溃时的进程现场，供调试器和分析工具事后检查。core dump 往往不仅包含程序本身的相关映像信息，还可能包含**运行时内存内容**。在Linux 中，core dump 常见会用 `PT_LOAD` 记录被转储的内存区域，用 `PT_NOTE` 记录寄存器、信号、 线程状态、辅助向量、映射文件信息等调试元数据。需要注意的是，用户栈、堆以及各类 `mmap` 区域并不是 无条件全部出现在 core 文件中；哪些映射会被真正转储，还会受到内核策略和进程设置的影响。

## Segment

`segment` 是 ELF 在**运行和加载视角**下最重要的组织单位。加载器并不是按 `.text`、`.data` 这种 section 名字来直接装载程序，而是主要通过 `Program Header Table` 中的各个 `segment` 来决定：哪些内容要被映射到内存、映射到什么虚拟地址范围、以及这些映射应当具备什么权限。

因此，segment 可以理解为“程序运行时内存布局的蓝图”。尤其是 `PT_LOAD` 类型的 segment，会直接对应进程地址空间中一段要被映射出来的内存区域。代码段、只读数据段、可写数据段等最终以什么样的虚拟地址关系出现在进程内存中，主要就是由这些 segment 决定的。

ASLR 会影响程序和共享库在进程地址空间中的**整体装载基址**，但不会改变同一个 ELF 内部各个 segment 之间的**相对布局**。也就是说，ASLR 会把整张“内存布局蓝图”整体平移到另一个位置，但不会把原本相邻的 segment 随机拆散，也不会改变它们之间由 ELF 描述出来的相对顺序和相对地址关系。这也是为什么 `ET_DYN` 虽然运行时基址可变，但各个 segment 的内部布局仍然保持稳定。

常见的 segment 类型包括：

- `PT_LOAD`：最重要的**可加载段**，描述哪些内容需要真正映射到进程内存中。
- `PT_INTERP`：给出程序所需**解释器的路径**，典型就是动态加载器 `ld.so`。
- `PT_DYNAMIC`：提供动态链接所需的信息入口，例如依赖库、重定位、符号解析相关元数据。
- `PT_PHDR`：描述程序头表自身在内存中的位置。
- `PT_NOTE`：保存附加说明信息；在 `ET_CORE` 中尤其重要，常用于保存寄存器、线程状态、信号等调试元数据。
- `PT_GNU_STACK`：描述进程栈的权限需求，例如是否需要可执行栈。
- `PT_GNU_RELRO`：标记一段在重定位完成后应转为只读保护的区域。

这些 segment 不是凭空独立出现的。对可执行文件和共享库来说，链接器会根据 section 的属性、用途和权限，把若干 section 组织进一个或多个 segment 中。比如 `.text` 和一部分只读内容常常会被放进同一个可执行或只读的 `PT_LOAD` 段，而 `.data`、`.bss` 等可写内容则常常进入另一个可写的 `PT_LOAD` 段。

因此，可以把它理解成：**section 更像“按语义分类的内容块”，segment 更像“按加载需求打包后的运行单元”**。前者更方便链接器和分析工具理解程序内容，后者更方便加载器把程序变成真正的进程内存映像。

## Section

`section` 是 ELF 在**链接、调试和静态分析视角**下最重要的组织单位。和 segment 更关注“程序怎样被装进内存”不同，section 更关注“这部分内容在语义上是什么”。因此，阅读 ELF 时，如果你关心的是代码、只读常量、全局变量、符号表、重定位信息这些内容应该如何分类和解释，那么通常就应该优先看 section。

section 可以看作是“按用途和语义切分出来的内容块”。链接器会根据这些 section 来完成符号解析、重定位和最终布局；调试器、反汇编器和静态分析工具也常常依赖这些 section 来判断某段内容究竟是机器代码、数据、符号信息，还是附加说明信息。

section 和 segment 不是彼此独立的两套数据。更准确地说，section 提供的是**语义视图**，segment 提供的是**加载视图**。对可执行文件和共享库来说，链接器通常会把多个语义上相关、权限上兼容的 section 组织进同一个 segment 中。因此，经常会出现“多个 section 共同落在一个 `PT_LOAD` 段里”的情况。

常见的 section 类型包括：

- `.text`：程序的机器代码，通常是可执行内容。
- `.rodata`：只读数据，例如字符串字面量、只读常量等。
- `.data`：已初始化的可写全局变量和静态变量。
- `.bss`：未初始化和**零初始化**的全局变量和静态变量；它在语义上存在，但在文件中通常不以普通数据块形式存储。也就是说这个 section 在 ELF 中更像一个占位，并**不占用真实的文件大小**，但是当它被拼入 segment、最终被加载进内存时是**要占用内存空间**的。`segment` 的 `p_memsz` 大于 `p_filesz` 就常常是这个原因导致的。
- `.data.rel.ro`：在加载时需要经过重定位修正、但重定位完成后又应转为只读的数据。很多带地址语义的只读对象会落在这里；**C++ 虚函数表也常见于这个 section**。（关于虚表的详细内容见[[运行时多态]]）
- `.symtab`：完整符号表，常用于链接和静态分析。
- `.strtab`：与符号表等配套使用的字符串表。
- `.dynsym`：动态链接相关的精简符号表。
- `.dynstr`：动态链接相关的字符串表。
- `.dynamic`：动态链接信息表，可以把它理解成运行时动态链接所需的“元数据目录”。其中会记录依赖库、动态符号表、动态字符串表、重定位表、初始化/析构函数等信息；这批数据通常会通过 `PT_DYNAMIC` 这个 segment 暴露给加载器。
- `.got`：Global Offset Table，用来保存运行时需要间接访问的一些地址信息，方便位置无关代码在运行时通过表项取地址；其中某些表项会在加载时通过重定位被修正。
- `.plt`：Procedure Linkage Table，和动态链接中的延迟绑定有关。可以粗略理解为“给外部函数调用准备的一层**跳板代码**”。
- `.got.plt`：和 `.plt` 配合使用的 GOT 子区域，主要服务于外部函数调用的动态解析与跳转；外部函数第一次被解析后，真实地址通常会回填到这里。
- `.rela.*` / `.rel.*`：重定位表 section，用来描述**哪些位置需要被修正**，以及**应该按什么规则修正**。在可重定位目标文件 `ET_REL` 中，它们通常**和某个 section 关联**，例如 `.rela.text` 往往表示“和 `.text` 相关的重定位表”，也就是说这里的 `*` 很多时候对应被关联的 section 名字。到了可执行文件和共享库中，也会看到像 `.rela.dyn`、`.rela.plt` 这样按用途命名的重定位表。
- `.debug_*`：调试信息 section，供调试器使用。
- `.note.*`：附加说明信息，例如构建信息、ABI 信息等。

因此，可以把 section 理解成“**程序内容的语义目录**”。如果 segment 回答的是“这些字节怎样被装载进内存”，那么 section 回答的就是“这些字节在程序和工具链语义上分别代表什么”。

## 常用命令

看 ELF 基本类型和架构：
- `file a.out`

看 ELF Header：
- `readelf -h a.out`

看 Program Header / Segment：
- `readelf -l a.out`

看 Section Header：
- `readelf -S a.out`

同时看 header、segment、section 等整体信息：
- `readelf -a a.out`

看符号表：
- `readelf -s a.out`
- `nm a.out`
- `nm -D a.out`

看重定位表：
- `readelf -r a.out`

看动态段信息：
- `readelf -d a.out`

看依赖了哪些动态库：
- `ldd a.out`

反汇编代码：
- `objdump -d a.out`
- `objdump -D a.out`

反汇编时带上源码和符号信息：
- `objdump -S a.out`

看 section 和 segment 的映射关系：
- `readelf -W -l a.out`

只看某个 section 的原始内容：
- `readelf -x .text a.out`
- `readelf -p .rodata a.out`
- `objdump -s -j .data a.out`

看导出的动态符号和版本信息：
- `readelf --dyn-syms a.out`
- `readelf -V a.out`

快速搜二进制里的字符串：
- `strings a.out`

如果只是想快速观察一个 ELF，通常最常用的一组是：
- `file a.out`
- `readelf -h -l -S -s -r -d a.out`
- `objdump -d a.out`
- `ldd a.out`
