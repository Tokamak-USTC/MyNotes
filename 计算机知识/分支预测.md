## 速览

- 编译器仅做静态布局，不直接干预运行时预测；`likely`是告诉编译器冷热属性，不是告诉CPU跳或不跳。
- 2-bit饱和计数器是置信度，不是最近两次跳转记录；单次反转仅降级，连续两次才翻向预测方向。
- GHR是全局分支流水账，和PC做XOR后索引PHT，让同一条分支在不同上下文下落入不同slot。
- GShare用样本摊薄换上下文感知，是工程上的合理权衡；TAGE通过分层+Tag解决了GShare的缺陷。
- 静态规则是兜底：向前跳默认不跳，向后跳默认跳，`ret`优先走RSB。

## 分支指令流的常见形式

程序编译后，分支在指令流中以三类核心形态存在：

- **条件分支**：对应高级语言的`if/for/while`，汇编指令为`jcc`（如`jle`/`jne`），跳转目标地址固定，是分支预测器的主要处理对象。
- **间接分支**：对应`switch`跳转表、虚函数调用、函数指针调用，汇编指令为`jmp reg`，跳转目标不固定，需要额外预测目标地址。
- **返回指令**：对应`ret`，跳转目标取决于调用栈，不遵循普通条件分支的预测逻辑。
- **冷热路径特征**：
	- 热路径：高频执行的顺序指令流，占程序运行时间的90%以上，是优化的核心关注对象。
	- 冷路径：低频执行的跳转目标（如错误处理、边界检查），几乎不占用CPU缓存和预测器资源。

## CPU的动态分支预测机制

### 静态预测（无历史时的默认行为）

当分支首次执行、预测器无任何历史记录时，采用硬件硬编码的兜底规则

- **向前跳（目标地址>当前PC）**：默认预测「不跳（Not Taken）」，对应普通`if`跳过冷路径的场景。
- **向后跳（目标地址<当前PC）**：默认预测「跳（Taken）」，对应循环回绕的场景。
- **`ret`指令**：不使用上述规则，直接查询**RSB（返回栈缓冲区）**：`call`执行时将返回地址压入RSB栈，`ret`执行时弹栈获取目标，几乎100%命中。
- 上下文切换/低功耗唤醒时，部分预测器状态会被清空，短期退化到静态规则。

### PHT：分支局部历史管理

PHT（Pattern History Table，模式历史表）是存储**分支自身跳转历史**的核心结构，本质是2-bit饱和计数器的集合，决定的是某个分支指令**跳**还是**不跳**，即 taken 还是 not taken

#### 2-bit饱和寄存器

- 状态机：
	- 该寄存器的值可以取 `00`, `01`, `10`, `11`，
	- 如果某个分支被采纳，则其对应的寄存器值 +1，至多到 `11`，
	- 未采纳则 -1，至多到 `00`
- 使用方式：
	  - 如果某条分支跳转指令的饱和寄存器值 **>=2** 则采纳
	  - **<=1** 则不采纳
- 核心局限：仅记录单条分支的历史，看不到前面其他分支的影响，无法处理上下文相关的分支。

#### PHT

- 索引方式：用分支指令的PC（地址）低K位哈希作为索引，K=log2(PHT条目数)。
- 哈希冲突：不同PC的分支哈希到同一个PHT条目，互相覆盖计数器状态，是PHT固有的代价，靠增大PHT容量缓解。

### GHR：全局历史与跨分支上下文

GHR（Global History Register，全局历史寄存器）是解决“上下文相关分支”的核心，本质是一个移位寄存器，按时间顺序记录**最近N次所有分支的真实跳转结果**（跳=1/不跳=0，和PC值共同索引PHT条目，决定跳还是不跳

- **与PHT的配合（GShare预测器）**：
	- 索引算法：`index = PC_low_K XOR GHR_low_K`，通过XOR将PC和全局历史揉合，让同一条PC在不同全局上下文下落入不同的PHT条目。
	  - 预测流程：取指时读取当前GHR→计算索引→查PHT得到2-bit状态→预测方向→分支退休后更新PHT+GHR左移塞入本次真实结果。
- **核心关注点：样本摊薄问题**：
	  - 若某条`jle C`仅依赖前两条分支`jle A/B`的结果（共4种有效上下文），理想情况下仅需4个PHT slot存储历史。
	  - 若K=8，GHR低8位全参与XOR，会导致这4种有效上下文每种都被打散到`2^(8-2)=64`个slot，总覆盖256个slot。
	  - 本质不是传统哈希碰撞（不同分支争抢同个slot），而是**同一条分支的历史样本被摊薄到多个slot**，单个slot的训练强度下降。
	- **噪声问题**：GHR记录所有分支的结果，对单条`jle`而言，大部分高位是无关分支的噪声，但真实程序中噪声位在执行区域内是稳定的，仅造成固定偏移，不会完全破坏预测。
	- **权衡逻辑**：用样本摊薄的代价换取上下文感知能力，热路径高频执行足以抵消摊薄影响，整体预测命中率仍远高于纯PHT。

### BTB：分支目标地址缓存

BTB（Branch Target Buffer，分支目标缓冲区）解决的是“**跳到哪里**”，而不是“**跳不跳**”。对条件分支、无条件跳转、函数调用、间接跳转等控制流指令，前端往往希望在还没有完整解码出目标地址之前，就提前知道下一拍应该从哪里继续取指。

- **核心职责**：若方向预测器判断本次分支大概率会跳转，BTB 就给出这条分支对应的目标地址 `target`，让取指单元直接从目标位置继续取指。
- **和 PHT / GHR 的分工**：
	- `PHT / GHR / TAGE` 这类方向预测结构回答的是 `taken / not taken`
	- `BTB` 回答的是 `taken` 之后跳到哪个地址
	- `ret` 往往优先使用 `RSB`，而不是普通 BTB
- **为什么直接分支也需要 BTB**：虽然像 `jcc rel32` 这类直接分支的目标最终可以由 `PC + offset` 算出来，但前端在很早阶段往往还没来得及完整解码指令；如果每次都等到 decode 后再算目标，取指流就可能断掉。BTB 的价值在于**提前缓存目标地址**，避免前端等待。
- **最简化的理解方式**：可以近似把 BTB 看成 `branch PC -> target address` 的映射表。某条 branch 第一次真实执行并解析出目标地址后，硬件可以把 `PC` 和 `target` 写进 BTB，供下一次遇到同一条 branch 时直接使用。

#### BTB 的组织方式

- **本质上更像一个小型 cache**，而不是一张理想的字典表。
- **常见表项内容**：
	- `valid`
	- `tag` 类似 cache 的tag，快速查找某个PC值是否命中一个BTB
	- `target` 存储指令的**实际跳转位置**
	- 可选的 `branch type` 等元数据
- **查找流程**：
  - 用 branch `PC` 的低位选中一个 `set`
  - 在这个 `set` 的若干个 `way` 里比较 `tag`
  - 若命中，则返回该表项中的 `target`
  - 若未命中，则说明暂时没有可用的目标预测
- **碰撞处理**：
  - 多条不同的 branch 可能落到同一个 `set`
  - 只要 `way` 还有空位，它们就可以共存
  - 若 `set` 已满，而新的 branch 又需要写入 BTB，就要按替换策略**淘汰一个旧表项**

#### BTB 对间接跳转的意义

- **对直接跳转**：BTB 的主要价值是让前端更早拿到目标地址，避免等待解码。
- **对间接跳转**（如虚函数调用、函数指针调用、`switch` 跳转表）：目标地址并不直接写在指令里，而是要等运行时从寄存器或内存里取出；这时 BTB 或更专门的间接目标预测结构就更重要。
- **对虚函数调用**：调用点本质上通常是 `call reg` 一类的间接调用。同一个调用点如果在运行时大部分时候都落到同一个具体实现，预测器就有机会提前猜中目标函数，让前端提前取它的指令，从而减少断流。

#### 虚函数调用场景下，BTB 做了什么

以 `p->foo()` 这种虚调用为例，机器级上通常不会直接变成 `call fixed_label`，而更像是：

- 先从对象里取出 `vptr`
- 再从 `vtable` 里取出 `foo` 对应的函数地址
- 最后执行 `call reg` 这类间接调用

问题在于：前端在很早阶段只看到了“这里有一条间接调用指令”，但这次真正会跳到哪个函数体，要等后面的访存和地址解析完成后才能完全确定。如果什么都不预测，前端就只能停下来等真实目标地址出来，取指流容易断掉。

BTB 在这个场景下做的事可以近似理解为：

- 以前遇到这条调用点 `PC` 时，硬件观察到它最终跳到了某个具体实现，例如 `Derived::foo`
- 于是把这条调用点 `PC` 和对应的目标地址缓存下来
- 下一次前端再次取到这条虚调用时，即使 `vptr` 和 `vtable` 里的真实地址还没完全读出来，BTB 也可以先猜“这次大概率还是去 `Derived::foo`”
- 前端于是提前从 `Derived::foo` 对应的位置开始取指
- 如果后面真实解析出来的目标地址确实也是它，流水线几乎不断流；如果猜错了，再刷流水线并跳到真正的目标

因此，BTB 在虚函数调用场景里的核心价值不是减少那几次访存，也不是替代 `vtable` 查找，而是**在真实目标地址尚未解析完成时，先给前端一个高概率的目标地址猜测**，让前端不要闲着。

## 编译器的优化

编译器**无法直接命令CPU在运行时选择跳或不跳**，仅通过调整代码布局和传递语义信息，为CPU预测器创造“容易预测”的环境

- **核心目标**：顺应CPU静态预测规则，让热路径尽可能走顺序执行（Fall-through），避免预测失败带来的流水线清空开销。
- **布局规则**：
	  - 无提示的普通`if`：默认将`if`块放在**向前跳转的目标（冷路径）**，热路径走Fall-through，命中CPU“向前跳默认不跳”的静态规则。
	  - `[[likely]]`/`__builtin_expect`：显式告诉编译器`if`块为热路径，将`if`块放在Fall-through位置，冷路径放到高地址区。
	  - `__attribute__((cold))`：标记冷函数，将其放到独立的`.text.unlikely`段，与热路径物理隔离，避免污染I-cache和预测器资源。
- **辅助手段**：
	  - 分支hint前缀（如x86的`0x2E`/`0x3E`）：给静态预测器发送提示，现代高性能CPU（Intel Ice Lake+、AMD Zen、Apple M系列）大多忽略，仅在首次执行或老旧CPU上生效。
	  - 不会修改CPU内部的PHT/GHR/RSB等硬件状态，仅通过指令排布间接影响预测结果。
	  - `PGO`（Profile-Guided Optimization，基于 profile 的编译优化）：先让程序在真实或接近真实的 workload 下跑一遍，收集哪些分支更热、哪些调用点更常落到哪个目标、哪些 basic block 更常连在一起，再用这些 profile 数据重新编译。这样编译器就不必只靠静态猜测来决定代码布局、内联、冷热路径拆分和间接调用优化，对分支预测和前端取指通常更友好。
